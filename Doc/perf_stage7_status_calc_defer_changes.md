# Perf Этап 7 — отложенный (коалесцированный) пересчёт status_calc_pc на equip-swap

## ⚠️ Сделано по прямому запросу, НЕ поведенчески-идентично
В отличие от этапов 2–6 (поведение сохранено), этот этап **меняет поведение**: после экипа/снятия
полный пересчёт статов откладывается на следующий тик. Это сознательное решение пользователя
(см. развилку в сессии). Флаг по умолчанию ON; **`0` возвращает точное прежнее поведение.**

## Что сделано
`pc_equipitem`/`pc_unequipitem` раньше делали `status_calc_pc(sd,0)` синхронно на каждый предмет.
Теперь там вызывается `status_calc_pc_defer(sd)`:
- при `status_calc_defer: 1` — взводит one-shot таймер на `gettick()+1` (если ещё не взведён);
  несколько экипов в одном тике коалесцируются в **один** пересчёт на следующем тике;
- при `0` — немедленный inline-пересчёт (как раньше).

Сопутствующее:
- `status_calc_pc_flush(sd)` — принудительный пересчёт сейчас; вызывается в `chrif_save` (перед
  снимком для сохранения), чтобы сохранённые/отображаемые статы были свежими.
- Любой **синхронный** `status_calc_pc` (левелап, смена джоба, рефайн, логин и т.д.) отменяет
  висящий отложенный таймер — он его подменяет (нет лишнего повторного пересчёта).
- Таймер-cb защищён `map_id2sd` + сверкой tid → нет use-after-free при релоге/выходе до срабатывания.
- Только два канонических места equip-swap переведены на defer (pc_equipitem, pc_unequipitem).
  Ревалидация предметов при смене карты (`pc_checkitem`-путь) и все прочие ~30 вызовов
  `status_calc_pc` остались **синхронными** — минимизирует область изменения.

## Известные поведенческие отличия (риск, принят)
В пределах ~1 тика после экипа/снятия «свежих» статов ещё нет:
- **OnEquip/OnUnequip item-скрипты** читают статы ДО пересчёта (напр. `percentheal` по новому MaxHP
  применится к старому MaxHP; `readparam(bAtk)` вернёт старое значение).
- Проверка снятия **SignumCrucis** (`pc.c`, сразу после unequip) видит старые race/def_ele.
- Клиент получает обновление статов на ~1 тик позже.
- Атака в тот же тик, что и экип, использует старые статы оружия.
Логин (`first&1`) остаётся синхронным — на загрузку не влияет.

## Почему выигрыш мал
`status_calc_pc` вызывается **по событиям** (экип/левелап/логин), **не per-tick**; churn баффов
идёт через `status_calc_bl` (SCB-делта). Поэтому выигрыш — только в редком кейсе «много экипов за
один тик» (скрипт, одевающий комплект). Под боевой нагрузкой 300 онлайн это почти не влияет на CPU.

## Флаг
`conf/battle/misc.conf`:
```
status_calc_defer: 1   // 1 = коалесить equip-swap пересчёт (поведение меняется!); 0 = старый inline
```
(battle_config; `@reloadbattleconf` для A/B.)

## Чек-лист тестировщикам (фокус на корректности!)
- [ ] **OnEquip-эффекты:** предметы, чей OnEquip лечит/баффает/читает статы — ведут себя как при `0`?
      (если есть расхождения — это ожидаемый эффект отсрочки; сравнить с `0`.)
- [ ] Экип/снятие комплекта: итоговые статы корректны (через тик), HP/SP-максимумы верные.
- [ ] **SignumCrucis**: снятие экипа, влияющего на расу/элемент, корректно снимает/оставляет проклятие.
- [ ] Сохранение/релог: статы после релога верные (flush в chrif_save).
- [ ] Быстрый экип → атака: нет «удара по старым статам», ломающего баланс (если критично — `0`).
- [ ] Нет крэшей при массовых экипах/релогах/выходе во время висящего пересчёта.
- [ ] **Рекомендация:** если хоть один предмет полагается на OnEquip-статы — ставить `status_calc_defer: 0`.

## Откат
`status_calc_defer: 0` (+ `@reloadbattleconf`) — мгновенно возвращает прежнее поведение.

Сборка чистая; локальный буст онлайн; `status_calc_defer` парсится; cb UAF-безопасен.
