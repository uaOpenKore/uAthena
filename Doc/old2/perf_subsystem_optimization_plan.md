# План: поэтапная оптимизация CPU подсистем map-server (сеть + игровая логика)

**Цель:** снизить потребление CPU игрового потока map-server под целевой нагрузкой
(~300 онлайн, pre-ep12 WoE/GvG с плотной кучей игроков, клиент 2007 / PACKETVER 7), разрешено
тратить RAM на буфера/кеши/таблицы ради более дешёвых алгоритмов. Источник — анализ 4 подсистем
(приём / отправка / пакетирование / прочая игровая логика), проведённый 2026-06-16.

**Делаем ВСЁ постепенно**, по этапам. Каждый этап: самодостаточен, собирается+бутится чисто,
коммитится отдельно, имеет отчёт для тестировщиков и (где можно) standalone-тест.

---

## Уже сделано (НЕ переделывать — ground truth по текущему коду)

- **Сеть-ядро:** `do_sendrecv` уже на **epoll** (`socket.c`, `SOCKET_MAX=32768`, select/FD_SETSIZE
  убраны). `TCP_NODELAY` на каждом сокете. `setrlimit` поднимает лимит fd.
- **Отправка:** off-thread **send-worker** (`send_worker.c`, `socket_async_send`) + **коалесинг**
  (реальное ms-окно `socket_send_coalesce_ms`), оба **включены в проде** (`conf/battle/misc.conf`:
  `socket_async_send:1`, coalesce `10ms`). Модель безопасности воркера (owned-copies, стабильный
  fd-массив, close-sync на `g_close_cv`) — сохранять при любых правках send-пути.
- **clif_send AREA:** broadcast-буфер строится **один раз** и `memcpy`-ится всем получателям —
  перестройки на каждого нет (это правильно, не трогать).
- **SQL/логи:** async log writer (`log_async.c`), `async_db`, mapreg/mail off-tick.
- **Mob AI:** flat-array `livemob`, `mobgrid` (`block_pc_count` грид), `mob_ai&0x20` опты
  (skip-noplayer, active-maps-only, 250ms PC-near probe cache); убраны per-tick id_db-сканы
  (natural-heal → `map_foreachpc`, lazy mob AI → `livemob`). RNG — central `rnd()`.
- **НЕ хотспоты** (подтверждено): `timer.c` (min-heap, O(log n)); buff/debuff churn (узкие
  `SCB_*`-флаги); `map_addblock/delblock` (O(1)); DBMap point-lookups; `bl_list` (статик).

## Сквозные соглашения (для ВСЕХ этапов)

1. **Флаг на каждую оптимизацию.** Поведенческие/структурные изменения — за `battle_config`
   (игровая логика, парсится в `battle.c`, conf в `conf/battle/*.conf`) или за socket-уровневой
   глобалью, которую map.c выставляет из `misc.conf` (как уже сделано для `socket_async_send`).
   Это даёт тестировщикам **A/B в одной сборке** (flag 0 vs 1 на одинаковой нагрузке под
   `UA_PERF=1`). Дефолты: чисто-поведение-сохраняющее → можно `1`; то, где есть риск инвалидации
   кеша → дефолт `0`, тестировщики подтверждают корректность, потом отдельным коммитом флипаем `1`.
2. **Отчёт для тестировщиков на каждый этап** — `doc/perf_<этап>_changes.md`, содержит:
   *что изменилось*; *имя флага(ов) + дефолт + как включить/выключить*; *как замерить* (A/B,
   одинаковая нагрузка, `UA_PERF=1`, какой хотспот должен просесть в профиле); *чек-лист
   корректности* (специфичные регрессии для этого изменения); *откат* (flag=0).
3. **Коммит на под-задачу.** Перед push: `git fetch origin x64` + `git rebase origin/x64`
   (**Cline Bot `<bot@pechsoft.com>` пишет в x64 параллельно** — всегда rebase перед push).
   Футер коммита: `Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>`.
   НЕ коммитить `eathena_mechanic_changes.md` (не моё) и `log/` (рантайм).
4. **Верификация на этап:** `make sql` без новых ворнингов + boot-clean (оба сервера линкуются и
   стартуют). Для структур данных / потоковых модулей — standalone ASan/UBSan(/TSan) тест
   (как `test_livemob.c`/`test_mobgrid.c`/`test_send_worker.c`; собираются отдельным `-D…_TEST`,
   не входят в `make sql`). `GNUmakefile` генерится из `Makefile` — править `Makefile`.
5. **Инвариант корректности кешей:** кеш на объекте/карте обязан инвалидироваться на ВСЕХ путях,
   меняющих кешируемое (move/death/warp/logout/changelook/…). Дисциплина — как у `livemob`
   (`idx<0` skip, снапшот под `map_freeblock_lock`). Сначала узкий скоуп (напр. только GvG-карты),
   потом расширение.
6. **Измерять до флипа дефолта.** % между разными прогонами «рыхлые» — выводы делаем только из
   A/B одного бинарника. Реальный профиль = тестировщики на кластере с ботами (здесь без клиента
   карты/мобы не грузятся).

## Этап 1 — Дешёвый пакет (низкий риск, почти поведение-сохраняющее)

Четыре мелкие победы одним этапом, по коммиту на каждую, один общий отчёт.

### 1a. `SO_SNDBUF` (S-4)
- `socket.c` (~`:156`, закомментировано): выставить `SO_SNDBUF` (~256 КБ) на клиентских сокетах.
  Мотив: при WoE-бурсте маленький sndbuf → EAGAIN → немедленный флаш + 5ms-ретрай в воркере →
  коалесинг не работает. RAM: ~300×256КБ ≈ 75 МБ.
- Флаг: `socket_sndbuf_size` в `misc.conf` (0 = не трогать = старое поведение; >0 = байт).
- Риск: low (только память ядра/сокет).

### 1b. Pathfinding scratch без полного `memset` (G-3)
- `path.c` `path_search_real` (~`:308-370`): сейчас `struct tmp_path tp[32*32]`≈12 КБ на стеке +
  `memset` целиком на каждый A*-fallback. Сервер однопоточный → сделать `tp` **статическим
  переиспользуемым** scratch и **очищать только тронутые клетки** (трекать через open-list/
  «поколение»-штамп вместо memset). Fast straight-line пред-проход оставить как есть.
- Флаг: не обязателен (поведение-идентично); но для A/B можно `path_scratch_reuse` (дефолт 1).
- Риск: low (нельзя оставлять stale-клетки между вызовами — поэтому штамп поколения, а не memset).

### 1c. `packet_db` hot/cold split + вынос len-лука из цикла (R-2 / R-3 / F-4)
- `clif.h`/`clif.c`: `packet_db[23][769]` сейчас 56-байт struct (967 КБ), на диспатче нужны только
  `len`+`func`. Сплит на **hot** `{short len; void(*func)()}` (~276 КБ) и **cold** `pos[20]`
  (отдельная таблица, индексится только хендлерами). В `clif_send`/`clif_send_sub` и ветках
  `clif_send` — вычислить `len`/валидность **один раз** до фан-аута, убрать `packet_db[ver][op]`
  лук с каждого получателя (предполагаем единый PACKETVER; оставить per-target за «mixed-ver» fast
  path-гейтом на всякий). В горячих хендлерах (move/attack/pickup) — локально кэшировать `pos`.
- Флаг: `packet_db_hotsplit` для A/B (дефолт 1) — или без флага, т.к. поведение-идентично.
- Риск: low-med (механика; обновить ~42 сайта доступа к `pos[]`).

**Отчёт:** `doc/perf_stage1_cheap_changes.md`.
**Верификация:** build/boot clean; для 1b — прогнать существующие path-related сценарии (или
мини-тест `path_search` на нескольких картах в standalone харнессе, если осилю без полной карты).

## Этап 2 — Наземные AoE: `skill_unit_timer` (G-1 + G-2) — главный пропущенный хотспот

**Текущая беда:** каждые 100мс `skill_unit_timer` (`skill.c:~10409`) делает
`map_foreachobject(BL_SKILL)` — сканирует **весь глобальный `objects[]` без гейта по картам/
игрокам**, и на каждый живой unit — `map_foreachinshootrange` с `path_search_long` (LoS) на
каждого кандидата. На WoE: 150-400 живых AoE-клеток × LoS на ~10-15 игроков × 10/сек.

**Зеркало уже проверенного `livemob`/`mobgrid`:**
- **2a. Per-map список живых skill-unit** (новый `src/map/liveskillunit.c` или встроить рядом с
  livemob): contiguous массив `skill_unit*` на карту (или глобально с map-id), O(1) swap-remove,
  индекс кешится в самом unit; снапшот под `map_freeblock_lock`, skip удалённых по `idx<0`.
  `skill_unit_timer` итерирует только живые units на **картах с `users>0`** (как
  `mob_ai_active_maps_only`). Регистрация/удаление — в `skill_initunitgroup`/`skill_delunit`
  (lockstep с lifetime — критично).
- **2b. Player-presence гейт:** перед `foreachinshootrange` юнита проверять `block_pc_count`
  (грид `mobgrid` уже построен) в радиусе `unit->range`; нет PC рядом → пропуск (юнит всё равно
  никого не заденет этот тик). Учесть юниты, бьющие по себе/владельцу (traps и т.п. — не пропускать
  по неверному условию).
- **2c. LoS-мемоизация** `path_search_long` в `map_foreachinshootrange` (`map.c:~716`): TTL-кеш по
  паре клеток (источник-юнит → цель) в пределах тика (стены статичны, цели двигаются ≤1 клетку/тик);
  либо per-skill гейт `skill_wall_check` (многим AoE LoS не нужен). Аккуратно с Pneuma/Safety Wall
  кромками.

- Флаги: `skill_unit_active_maps_only` (дефолт 1), `skill_unit_skip_noplayer` (дефолт 1),
  `skill_unit_los_cache` (дефолт 1) — в `conf/battle/skill.conf`.
- **Standalone-тест** `test_liveskillunit.c` (как `test_livemob.c`): enqueue N units, snapshot/
  drain, swap-remove, delunit mid-pass → idx<0 skip. ASan/UBSan-clean.
- **Чек-лист корректности (для отчёта):** AoE наносят урон как раньше (Storm Gust/LoV тикают),
  ловушки срабатывают, Pneuma/Safety Wall/Magnetic Earth корректны, юнит исчезает по таймеру,
  массовая смерть в AoE не крашит, поведение на пустой карте = юниты живут но не сканируют.
- Риск: med (lifetime lockstep + LoS-кромки). Win: очень высокий.

**Отчёт:** `doc/perf_stage2_skillunit_changes.md`.

## Этап 3 — Приём: parse-shortlist (R-1)

**Текущая беда:** `do_parsepacket` (`socket.c:~584-610`) брутфорсит `1..fd_max` с indirect-call
`func_parse` + `RFIFOFLUSH` на **каждую** сессию каждый тик, хотя epoll уже знает, у кого данные.

- **3a.** Зеркало уже существующего `send_shortlist` (`socket.c:~1106-1161`): `recv_to_fifo` при
  `len>0` кладёт fd в **parse-shortlist** (флаг `in_parse_list` в `socket_data`, массив
  `int[SOCKET_MAX]`≈128 КБ). `do_parsepacket` идёт только по этому списку. fd с буферизованным
  частичным/множественным пакетом должен **оставаться** в списке (re-arm, пока `RFIFOREST>1`).
- **3b.** Sweep stall-timeout (единственная причина трогать idle-сессии) вынести в отдельный таймер
  раз в ~1 сек, а не каждый тик.
- Флаг: `recv_parse_shortlist` в `misc.conf` (дефолт 1; 0 = старый брут-скан для A/B и отката).
- **Чек-лист:** все пакеты обрабатываются (нет «залипших» частичных), таймаут-дисконнект работает,
  flood/partial-packet корректны, реконнект-буря ок.
- Риск: med (нельзя «потерять» fd с недопарсенным буфером). Win: высокий.

**Отчёт:** `doc/perf_stage3_recv_shortlist_changes.md`.

## Этап 4 — Фан-аут broadcast: кеши в `clif.c`

### 4a. Кеш списка зрителей AREA (F-2) — КЛЮЧЕВОЙ ускоритель всех broadcast'ов
**Беда:** каждый broadcast заново строит `bl_list` по 16 блок-ячейкам + фильтр по координатам
(`map.c:~791-801`). Стоящий скилл-спамер в куче пересобирает один и тот же список десятки раз/сек.
- На `unit_data` (или `block_list`) кеш: `struct block_list **area_viewers; int viewer_count;
  int viewer_cell/tick;` (PC-зрители в AREA актора). Инвалидация при **пересечении блок-ячейки**
  (`map_moveblock`) и на `map_addblock`/`map_delblock`/`clif_insight`/`clif_outsight`/death/warp/
  logout. `clif_send AREA*` итерирует кеш напрямую; WOS/WOC/WOSC-фильтры остаются per-зритель.
- Стоячий актор → список константен между его перемещениями → пересборки нет (ровно WoE-кейс).
- Флаг: `clif_area_viewer_cache` в `misc.conf`/`battle` — **дефолт 0** (рисковая инвалидация;
  тестировщики валидируют корректность, затем отдельный коммит флипает 1). Сначала скоуп — только
  `map_flag_gvg` карты.
- **Чек-лист (жёсткий):** ни одно видимое действие не «пропадает» у соседей; нет отправок ушедшим/
  телепортнувшимся; вход/выход из зоны видимости корректен; смена карты; смерть/респаун; стелс
  (cloaking) и disguise не ломают список.
- Риск: med-high. Win: очень высокий (переиспользуется КАЖДЫМ broadcast).

### 4b. Кеш байтов spawn-пакета на `bl` (F-1)
**Беда:** вход в кучу из V игроков → O(V) тяжёлых сборок `clif_set0078` (каждая дёргает
`status_get_sc/viewdata/guild_id/emblem_id/lv/speed` + `memset`).
- `uint8 spawn_pkt[…]; bool spawn_dirty;` на `bl`/`unit_data`, ленивая сборка, инвалидация по
  `clif_changelook`/opt1/opt2/option/emblem/dir/speed/sit-stand/level-up. `clif_getareachar_unit`
  для idle (0x22a) → `memcpy` вместо сборки. Walking-пакет (0x22c, несёт live tick/to_x/to_y) и
  disguise/cloth-refresh пути — НЕ кешировать (bypass). Начать с pet/NPC/mob (нет equip-churn,
  ниже риск), затем PC.
- Флаг: `clif_spawn_packet_cache` (дефолт 0 → после валидации 1).
- **Чек-лист:** spawn выглядит корректно после смены экипа/причёски/цвета/эмблемы/уровня/позы;
  disguise ок; моб/пет/NPC spawn ок.
- Риск: med. Win: высокий (самая дорогая единичная сборка в самом «текучем» пути).

### 4c. `cloth_color`: убрать 2-й проход AREA (F-3)
**Беда:** для крашеного перса каждый spawn/move делает второй полный проход AREA через
`clif_refreshlook(LOOK_CLOTHES_COLOR, AREA_WOS)` — а цвет уже в spawn-пакете 0x22a. На WoE
крашеные почти все → удвоение фан-аута.
- Для **spawn** пути убрать отдельный refresh (цвет уже в 0x22a — подтвердить, что клиент 2007
  его чтит). Для **move** (0x86 без look-полей) — слать refresh только при реальной смене цвета
  (dirty-флаг), а не каждый шаг.
- Флаг: `clif_clothcolor_inline` (дефолт 0 → после подтверждения клиентом 1).
- Риск: low-med (зависит от поведения клиента PV7). Win: высокий для крашеных.

**Отчёт:** `doc/perf_stage4_broadcast_changes.md` (общий на 4a-4c, с раздельными флагами/чек-листами).

## Этап 5 — Структурная отправка: `socket.c` / `send_worker.c`

Поверх уже работающего воркера+коалесинга. По возрастанию риска. Расширить `test_send_worker.c`
(TSan/ASan) на каждую под-задачу.

### 5a. Per-fd freelist чанков (S-3)
**Беда:** `sendworker_send` `malloc`-ит свежий `sw_chunk` на каждый пакет на каждого получателя и
`free`-ит после send — кросс-тредная нагрузка на аллокатор (game-thread malloc, worker free).
- Пул переиспользуемых чанков (per-fd или глобальный freelist под уже-берущимся `g_mtx`).
  Поднять `wfifo_size` (`socket.c:~62`, сейчас 16К), чтобы realloc-doubling inline-пути не срабатывал.
- Флаг: `send_chunk_freelist` (дефолт 0 → 1). Риск: med (cap на размер пула; кросс-тред free).

### 5b. `writev`/scatter-gather в воркере (S-2)
**Беда:** merge-коалесинг делает `malloc`+`memcpy` (copy#3) чтобы слить chunks (`send_worker.c:
~201-216`).
- Вместо merge — `writev`/`sendmsg` с `struct iovec[]` (переиспользуемый, owned воркером),
  указывающим на `data+off` каждого chunk; ядро собирает само. Обобщить partial-write advance на
  пересечение iovec-границ. `IOV_MAX` cap → fallback на текущий per-chunk send.
- Флаг: `send_worker_writev` (дефолт 0 → 1). Риск: low-med (partial mid-iovec).

### 5c. Refcount shared broadcast-буфер (S-1)
**Беда:** broadcast копируется 2K раз (copy#1 в `wdata` + copy#2 в chunk воркера). Для K зрителей.
- `sendworker_send` refcount-вариант: `clif_send` строит блок 1 раз, refcount=K, в очереди fd —
  `{shared_buf, off, len, refptr}`. Decrement по завершении send, free на нуле. Идеально с 5b
  (shared read-only нельзя мержить — а writev не требует). Убирает copy#2 для broadcast.
- Флаг: `send_refcount_broadcast` (дефолт 0 → 1 после валидации). Риск: med-high (refcount lifetime
  кросс-тред; partial/coalesce с shared-буфером). Win: наивысший (бьёт WoE O(N²) по копиям).
- **Сохранить** модель безопасности воркера (owned-copies заменяются на refcounted-owned; close-sync
  на `g_close_cv` обязателен).

**Отчёт:** `doc/perf_stage5_send_struct_changes.md` (раздельные флаги/чек-листы; TSan-результаты).

## Этап 6 — Бой: кеш mastery/base-weapon-damage (G-5)

**Беда:** `battle_calc_base_damage`/`battle_addmastery` (`battle.c:~695/602`) переderives weapon level
+ `pc_checkskill` (skill-tree lookup) на каждый удар на каждую руку — данные, что `status_calc_pc`
уже знает.
- Кешировать mastery-бонус + диапазон base-weapon-damage в `status_data` игрока (пересчёт в
  `status_calc_pc`, который уже вызывается на смене оружия). Per-hit путь читает вместо derive.
- Флаг: `battle_mastery_cache` (дефолт 0 → 1). Риск: med (инвалидация на свап оружия — но он уже
  зовёт `status_calc_pc`). Win: med (высокая частота вызовов в масс-комбате).
- **Чек-лист:** урон идентичен до/после на разных оружиях/масте/руках; свап оружия пересчитывает.

**Отчёт:** `doc/perf_stage6_battle_changes.md`.

## Этап 7 (отложенный/опциональный) — delta-пересчёт `status_calc_pc` (G-4)

**Беда:** полный пересчёт (skill-tree + equip/card-скрипты) на КАЖДЫЙ свап экипа (WoE-макросы).
- Идея: кешировать распарсенные эффекты equip/card-скриптов, на смене экипа пересчитывать **дельту**
  вместо повторного прогона скриптов + `pc_calc_skilltree` (последнее меняется только на трату
  скилл-поинтов, не на экип).
- **Риск: high** — трогает только что бекпортнутую item-bonus подсистему, легко внести тонкие
  стат-баги. **Делать ПОСЛЕДНИМ и только если профиль тестировщиков подтвердит объём свапов.**
  Тяжёлая верификация (стат-диффы до/после на наборе экипа+карт).
- Флаг: `status_calc_pc_delta` (дефолт 0).

**Отчёт:** `doc/perf_stage7_statuscalc_changes.md` (если возьмёмся).

## Сверка плана с rental + mercenary-доделками (2026-06-16)

Проверка: не появилось ли новых hot-path / не изменились ли допущения плана после rental-бекпорта
и mercenary M7d.

**Rental — влияния на игровой тик map НЕТ.**
- `struct item` += `unsigned int expire_time` (+4 байта): маргинально больше копирования при операциях
  с предметом; на горячих путях не значимо.
- char-персистентность (+1 SQL-колонка load/save) — на char-сервере, off-tick.
- `pc_inventory_rentals`-таймер — per-владелец-аренды, срабатывает по истечении (НЕ per-tick).
→ План не затронут.

**Mercenary M7d — НОВЫЙ per-tick путь (минорный), масштаб ≤ числа игроков.**
- `merc_ai_hard` каждые 100мс → `clif_foreachclient(merc_ai_sub_foreachclient)` обходит ВСЕХ онлайн,
  чтобы найти владельцев мерков (`sd->md`). O(online)/100мс = на 300 это ~3000 NULL-проверок/сек —
  тривиально, но это ЕЩЁ один `clif_foreachclient`/100мс (плюс к network-анализу плана).
- **Главная стоимость:** per-merc auto-aggro `map_foreachinrange(…activesearch…, range2, BL_CHAR)`
  когда у мерка НЕТ цели и он простаивает. Аналог mob active-search. В бою мерки имеют цель (скан
  пропускается); idle-мерки у мастера сканят. Масштаб = O(idle-мерки × соседние блоки)/100мс,
  ограничен числом мерков (≤ online), НЕ общим числом мобов.
- Self-баф-цикл (M7d-5b): на idle-мерка — цикл по `MAX_MERCSKILL`=40 + SC-проверки/100мс — тривиально.

**Вывод:** 8 этапов плана (network + игр.логика) **держатся без изменений** — rental/merc их не меняют.
Merc-AI добавляет минорный per-tick путь, зеркальный уже понятному mob-AI active-search.

**Новый КАНДИДАТ (низкий приоритет, не отдельный крупный этап):** *throttle merc-AI auto-aggro* —
скан врагов реже (напр. 300-500мс) при сохранении melee/chase/skill на 100мс, ИЛИ скан только когда
мастер в бою/недавно атакован. Плюс при высокой доле мерков — «live-merc список» вместо
`clif_foreachclient` (как `livemob`). Делать ТОЛЬКО если профиль тестировщиков покажет заметную долю
merc-AI (вероятно нет при разумном merc-онлайне). Приоритет — ниже Этапа 6.

**Готовность к оптимизациям:** план актуален, можно стартовать этапы (рекоменд. порядок: 0 → 1 → 2 …).
Перед рисковыми этапами желателен baseline-профиль тестировщиков (0x20 + игроки + мерки).
