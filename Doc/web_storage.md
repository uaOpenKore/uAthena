# Вещи игроков и сайт: правила (SQL-версия)

Для программиста сайта. Здесь описано, как сайту безопасно работать с инвентарём, тележкой, складом Кафры
и гильд-складом, чтобы не было дюпов и потерь вещей.

## Главное правило
**Сайт никогда не пишет в таблицы вещей** (`inventory`, `cart_inventory`, `storage`, `guild_storage`):
ни `INSERT`, ни `UPDATE`, ни `DELETE`. Пока игрок в игре (и даже какое-то время после выхода), мап-сервер держит
его вещи **в памяти** и при сохранении записывает свою копию поверх базы:
- сайт убрал вещь, а в памяти она осталась → сервер запишет её обратно → **дюп**;
- сайт добавил вещь, а сервер о ней не знает → следующая запись её затрёт → **потеря**.

**Читать можно всегда.** Но пока игрок онлайн, в базе может быть состояние на момент последнего сохранения
(раз в несколько минут и при выходе). Показывайте это как «на момент последнего сохранения».

Менять вещи сайт может **только через заявки** (таблица `web_storage_request`, ниже). Сервер выполняет заявку сам,
в момент, когда игра не держит эти вещи в памяти.

## Где лежат вещи
| место | таблица | владелец | ячеек | заметки |
|---|---|---|---|---|
| инвентарь чара | `inventory` | `char_id` | 300 | `equip <> 0` — надето |
| тележка чара | `cart_inventory` | `char_id` | 600 | только если у чара есть тележка |
| склад Кафры | `storage` | `account_id` | 1000 | **один на аккаунт**, общий для всех чаров; отдельного «склада чара» нет |
| гильд-склад | `guild_storage` | `guild_id` | 2338 | открыть в игре может один член гильдии за раз |

Колонки строки вещи: `id` (номер строки — **не ссылка**, номера перенумеровываются при старте сервера),
`nameid`, `amount` (до 32766 в стопке), `identify`, `refine`, `attribute`, `card0..card3`, `expire_time`
(аренда, ≠ 0), `equip`.
Особые `card0`: 255 (0x00FF) — кованая вещь, 254 (0x00FE) — сваренная/созданная, у обеих создатель в
`card2 | card3<<16`; −256 (0xFF00) — яйцо питомца, номер питомца в `card1 | card2<<16`.

## Заявки: `web_storage_request`
Таблицу создаёт чар-сервер при старте. Сайт делает `INSERT`, потом читает статус.

| колонка | что писать |
|---|---|
| `account_id`, `char_id` | аккаунт и чар (чар должен быть на этом аккаунте) |
| `op` | `move` (перенести), `add` (выдать новую вещь, например магазин сайта), `remove` (забрать) |
| `src`, `dst` | `inventory`, `cart`, `storage`, `guild_storage`. `move`: оба; `add`: только `dst`; `remove`: только `src` |
| `nameid`, `amount` | предмет и количество (не стекуемые: до 100 за заявку) |
| `identify`, `refine`, `attribute`, `card0..card3` | «подпись» вещи: сервер берёт строки, совпадающие с ней полностью |
| `note` | что угодно для себя (кто/за что), сервер не читает |

Сайт читает: `status` — 0 ждёт, 1 выполнено, 2 отказ; `result` — причина отказа или почему ждёт;
`done_at` — когда выполнено.

Пример: «взять 10 Red Potion из гильд-склада в Кафру»:
```sql
INSERT INTO web_storage_request (account_id, char_id, op, src, dst, nameid, amount, note)
VALUES (2000123, 150456, 'move', 'guild_storage', 'storage', 501, 10, 'site user #77');
SELECT status, result FROM web_storage_request WHERE id = LAST_INSERT_ID();
```

### Когда сервер выполняет
- **Инвентарь, тележка, Кафра:** только если аккаунта **нет на сервере вообще**: не в игре, не в выборе
  персонажа, и у аккаунта **нет лавки автотрейда** (запись в `autotrade_shop`, даже если лавка сейчас не
  поднята: после рестарта мап-сервер её восстановит и будет продавать из тележки). После выхода из игры это
  может занять до 2–3 минут.
- **Гильд-склад:** только если его **сейчас никто не открыл** в игре. Нужен `guild_storage_lock: 1`
  в `inter_athena.conf` (иначе все такие заявки получают отказ).
- Пока условие не выполнено, заявка ждёт (`status = 0`, в `result` написано почему). Через
  `web_storage_wait` секунд (600) — отказ.
- Сервер проверяет заявки каждые 3 секунды, по 20 за раз, в порядке `id`.

### Алгоритм сервера по шагам
Каждые `web_storage_interval` секунд (3) чар-сервер берёт до 20 заявок со `status = 0` по порядку `id` и для каждой:

1. **Проверка заявки:** известны ли `op`, `src`/`dst` (подходят ли к `op`), количество 1…32766 (не стекуемых
   до 100), существует ли предмет; у стекуемого нет заточки/атрибута. Ошибка → отказ.
2. **Проверка чара:** есть ли чар, на этом ли он аккаунте; для гильд-склада: в гильдии ли и член ли её; для
   тележки: есть ли у чара тележка. Ошибка → отказ.
3. **Можно ли трогать вещи сейчас** (иначе заявка ждёт, в `result` причина; через 600 с ожидания → отказ):
   - заявка касается **инвентаря, тележки или Кафры** → аккаунта нет на сервере (в игре, в выборе персонажа,
     в автотрейде), у аккаунта нет лавки в `autotrade_shop`, и у сервера нет неудачных, ещё не записанных
     сохранений этого аккаунта (если есть, сервер сначала пробует их записать);
   - заявка касается **гильд-склада** → `guild_storage_lock` включён (иначе отказ), склад сейчас **никем не
     открыт** в игре, и неудачное сохранение гильд-склада (если было) записано.
   Пока выполняется шаг 4, другие запросы сервер не обрабатывает (он однопоточный), поэтому открыть склад или
   войти в игру «посередине» заявки нельзя.
4. **Выполнение:**
   - **приёмник** (`move`/`add`): хватит ли места. Стекуемая вещь кладётся в существующую такую же стопку
     (если сумма ≤ 32766), иначе нужна 1 свободная ячейка; не стекуемые: N свободных ячеек. Нет места → отказ,
     ничего не тронуто;
   - **источник** (`move`/`remove`): ищутся строки с той же «подписью» (`nameid`, `identify`, `refine`,
     `attribute`, `card0..3`), кроме надетых (`equip <> 0` в инвентаре) и арендованных (`expire_time <> 0`).
     Если в сумме меньше, чем просят → отказ, ничего не тронуто. Иначе списываются по порядку строк (целые
     строки удаляются, последняя уменьшается);
   - потом вещь **записывается в приёмник** (в стопку или новыми строками);
   - всё в одной транзакции, где таблицы это позволяют (InnoDB). Порядок «сначала списать, потом записать»:
     при сбое посередине вещь пропадёт, а **не задвоится**; в логе есть всё, чтобы вернуть её руками.
5. `status = 1`, `result = 'done'`, `done_at = NOW()`, строка `[WEBSTORAGE] … done` в логе.

### Что происходит с каждым хранилищем потом
- **Инвентарь и тележка чара:** игрок увидит изменения при следующем входе: мап-сервер загружает их из базы
  при входе персонажа.
- **Кафра:** при следующем открытии склада после входа: мап-сервер загружает склад аккаунта из базы при
  первом открытии после входа, а при выходе выбрасывает свою копию.
- **Гильд-склад:** при следующем открытии любым членом гильдии: с `guild_storage_lock: 1` мап-сервер каждый раз
  берёт его из базы. Пока склад открыт, его меняет только игра; заявка ждёт закрытия.

### Проверки (отказ с причиной в `result`)
- чар не на этом аккаунте; нет такого чара; нет такого предмета;
- для гильд-склада: чар не в гильдии или не её член;
- тележка без тележки;
- в источнике меньше, чем просят (надетые вещи и вещи в аренде не берутся);
- в приёмнике нет места (ячейки) или стопка превысит 32766;
- у стекуемой вещи указаны заточка или атрибут.

Вес сервер не проверяет: игрок с перегрузом увидит его при входе.

### Права
Кто имеет право на заявку, решает **сайт**: проверьте, что вошёл именно владелец аккаунта. Для гильд-склада
сервер требует только, чтобы чар был членом этой гильдии (как в игре: брать может любой член).

## Лог сервера
`[WEBSTORAGE] req=<id> move aid=… cid=… storage->guild_storage item=501 x10 …: done` или `REFUSED <причина>`.
