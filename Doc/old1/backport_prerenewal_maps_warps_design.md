# Дизайн: аддитивный бэкпорт локаций и варпов из дореневального eAthena

Дата: 2026-06-15. Ветка: `x64`. Источник: `/tmp/eathena-ref` (дореневальный eAthena, 898 карт против текущих 684 в uAthena).

Это часть более широкого порта реневального контента (локации, варпы, мобы, итемы — без поддержки
новых функций, NPC кроме 3-х профессий). **Данная спека покрывает только локации и варпы.** Мобы,
итемы и NPC — отдельные задачи.

---

## 1. Принципы (требования пользователя)

1. **Действующие локации и варпы остаются без изменений.** Diff к существующим файлам = только добавления.
2. **Новые локации и варпы только добавляются.**
3. **Существующие варпы не изменяются**, даже если в новом варианте у них сменились координаты
   (пример: `anthell` — оставляем старые координаты входа).
4. Когда новая карта в новом варианте **заменяет** старую по точке варпа (существующий варп
   «перенаправлен» на новую карту) — старый варп **сохраняем**, а отвергнутую точку входа/выхода в
   новую карту **документируем** для ручной доработки тестировщиками.
5. Сопроводительная **документация для тестировщиков**: что изменено и что проверять.

## 2. Технический контекст (проверено по коду, не по памяти)

- Карты читаются **прямо из GRF** (`conf/map_athena.conf: read_map_from_cache: 0`). Геометрия карт
  (`.gat`) — клиентские/деплой-данные; в репозитории мы работаем с `db/map_index.txt` (регистрация
  локации) и варп-скриптами (`npc/warps/`). Доступность `.gat` в GRF — забота деплоя/тестировщиков.
- Варп ключуется двумя осями:
  - **имя NPC** — глобально уникально; дубликат имени = ошибка загрузки сервера;
  - **исходный тайл** `(карта,x,y)` — два варпа на одном тайле затеняют друг друга.
- Подключение варп-файлов: `npc/scripts_warps.conf` строками `npc: npc/warps/<...>.txt`.
- uAthena **не имеет** движков `battleground.c` / `instance.c` и скрипт-команд `bg_*`/`instance_*`
  (в eathena-ref они есть). Бэкпорт движков в объём не входит → BG- и инстанс-карты недостижимы.

## 4. Алгоритм слияния (детерминированный, на каждый варп eathena-ref)

Рассматриваем только варпы в объёме §3 (исходят из новой карты ИЛИ ведут на новую карту).

1. **Имя NPC уже есть в uAthena** → существующий варп (возможно перенесён/перенаправлен редизайном).
   **Сохраняем версию uAthena без изменений.** Если EA-назначение ведёт на новую карту из объёма —
   запись **ВХОД-конфликт**. Не добавляем.
2. **Иначе исходный тайл занят** другим варпом uAthena → коллизия тайла. Сохраняем uAthena. Если EA
   ведёт на новую карту — запись **ВХОД-конфликт**. Не добавляем.
3. **Иначе (имя новое И тайл свободен)** → **добавляем** варп (в поддерево backport, §6).
4. Варп, **исходящий из новой карты** и ведущий на старую карту в точку, которая в uAthena занята/иная,
   либо дублирующий уже сохранённую связь (пример: `moc_fild20`→`anthell`, а в uAthena `anthell`
   входится из `moc_fild04`) — запись **ВЫХОД-конфликт**. Не добавляем.

Закомментированные (`//`) варпы eathena-ref игнорируются (неактивны в источнике).

## 5. Документ конфликтов (`doc/backport_warp_conflicts.md`)

Посекционно по новой карте. Схема пользователя:

```
## moc_fild20
# ВХОД: требуемая_точка(карта,x,y) -> ведёт_на_новой(карта,x,y) | СОХРАНЁН старый(имя: тайл->dest) | решение?
morocc,299,207     -> moc_fild20,36,177   | СОХРАНЁН moc005: morocc,302,207->moc_fild10,22,207       | решение?
moc_fild01,101,16  -> moc_fild20,210,342  | СОХРАНЁН mocf01-1: moc_fild01,101,16->moc_fild04,317,376 | решение?
# ВЫХОД: точка_на_новой(карта,x,y) -> ведёт_на_старой(карта,x,y) | примечание | решение?
moc_fild20,156,143 -> anthell01,35,263    | anthell в uAthena входится из moc_fild04 — НЕ менять     | решение?
```

- `ВХОД` — требуемая точка входа В новую карту (которую нельзя поставить автоматически, т.к. её тайл/имя
  заняты сохранённым старым варпом): где она должна быть → куда ведёт на новой карте → `решение?`.
- `ВЫХОД` — точка варпа на новой карте → куда она ведёт обратно в старый мир → `решение?`.
- Тестировщик заменяет `решение?` корректирующими данными (поставить вход по новым координатам /
  сменить выход / удалить варп / и т.п.) для последующей обработки.
- Колонка «СОХРАНЁН …» / «примечание» — справочная, чтобы тестировщик видел, с чем именно конфликт.

## 6. Раскладка файлов

- **Новые варпы** — изолированное поддерево `npc/warps/backport/` (новые файлы по областям, напр.
  `morroc_fild.txt`, `prontera_fild.txt`, `man_fild.txt`, `spl_fild.txt`, `guild_arunafeltz.txt`).
  Существующие файлы `npc/warps/**` **не трогаются**.
- Подключение — добавить строки `npc: npc/warps/backport/<файл>.txt` в `npc/scripts_warps.conf`
  (отдельной секцией с комментарием-маркером).
- **Регистрация локаций** — новые строки в конце `db/map_index.txt` отдельной секцией с
  комментарием-маркером (`// ===== Backport pre-renewal locations =====`).
- **Документы для тестировщиков** — `doc/backport_warp_conflicts.md` (конфликты) и
  `doc/backport_maps_warps_changes.md` (сводка изменений + чек-лист проверки).

## 7. Воспроизводимость и реализация

- Слияние выполняет **детерминированный скрипт** (`dumps/forge/backport-warps.sh` или
  `doc/backport-warps.sh`): читает оба дерева, применяет правила §4, генерирует (а) варп-файлы в
  `npc/warps/backport/`, (б) добавления в `map_index`, (в) `doc/backport_warp_conflicts.md`. Скрипт
  сохраняется в репозитории → результат воспроизводим и проверяем.
- Список карт каждого класса (§3) задаётся явными списками в скрипте (не эвристикой по префиксу), чтобы
  исключить случайный захват реневал-карт вне объёма.

## 8. Верификация

- **Целостность существующего**: `git diff` показывает только добавления; ни одна существующая строка
  в `npc/warps/**` и в верхней (действующей) части `db/map_index.txt` не изменена.
- **Уникальность имён**: 0 дубликатов имён NPC по всему `npc/` (включая backport-поддерево).
- **Коллизии тайлов**: 0 новых варпов на тайлах, уже занятых действующими варпами.
- **Загрузка**: map-сервер парсит backport-варпы без ошибок (smoke-boot лог чист по `warp`).
- **Полнота документа**: каждый отвергнутый по §4 варп присутствует в `doc/backport_warp_conflicts.md`
  ровно один раз; число записей = число отвергнутых.
- Коммит по этапам в `x64`, пуш в origin.

## 9. Этапы (для плана реализации)

1. Скрипт слияния + явные списки карт по классам; генерация в «сухом» режиме (только отчёт-счётчики).
2. `map_index` добавления (все локации §3) + проверка отсутствия дубликатов.
3. Варп-файлы backport по областям: Morroc-destroyed → Moscovia → Brasilis → Manuk/Splendide →
   WoE:SE Arunafeltz (по одному коммиту на область).
4. Генерация `doc/backport_warp_conflicts.md`.
5. Подключение в `scripts_warps.conf`; smoke-boot; проверки §8.
6. `doc/backport_maps_warps_changes.md` (сводка + чек-лист тестировщика).
